# 贡献切入点分析参考（Route B）

## 〇、准备工作（先执行）

阅读以下文件建立项目理解，文件不存在则跳过：

- README.md
- CONTRIBUTING.md
- CHANGELOG.md / HISTORY.md
- 项目主入口文件（main.py / index.ts / app.py 等）

然后输出目录结构（depth=3），标注核心模块目录，并用 2~3 句话描述：这个项目的核心机制是什么？（Agent 项目：核心 Agent 循环是什么？使用了哪种规划范式？）

> **前置：AI 政策检查（v3 硬性规则）**
> 读取 CONTRIBUTING.md 或仓库 policy，扫描 AI 生成代码限制关键词（ai-generated / ai generated / generated code /
> copilot / chatgpt / llm / no ai / do not use ai / prohibit ai）。判定口径：
> - **明确禁止**（如 "do not use AI" / "no AI-generated code"）：标注高风险，建议用户改用"理解需求后自行实现、
>   明确声明无 AI 辅助"的方式，或更换候选项目。
> - **有相关表述**（提及但不禁止）：提示人工确认口径，避免误判。
> - **无相关表述**：正常推进。
> `scripts/repo_health.py` 的输出已自动附带该检查结果（AI 政策: blocked / mention / ok / unknown）。

## 一、贡献类型与难度

| 贡献类型 | 说明 | 难度 |
|---------|------|------|
| 文档 / 翻译 | 门槛最低，容易被 merge | ⭐ |
| 修 Bug | 从 good first issue 开始 | ⭐⭐ |
| 补测试用例 | 很多项目测试覆盖率不足 | ⭐⭐ |
| 新增工具/集成 | 比如给 Agent 框架加一个新的 tool 支持 | ⭐⭐⭐ |
| 核心功能 | 先在 Issue 里讨论再动手，避免白做 | ⭐⭐⭐⭐ |

## 二、分析维度一：Issue 列表筛选

**先机筛再人工**：运行 `scripts/find_issues.py <owner/repo>` 自动完成以下硬条件的初筛与打分：

- 标签包含 `good first issue` / `help wanted`（默认，新手友好）；`--include-bugs` 可纳入 bug/enhancement
- 状态为 open，近 60 天内有过活动（非 stale）
- 无 assignee，且**未被任何 open PR 引用**（撞车检测，脚本自动剔除）
- 脚本输出 0~100 启发式打分（清晰度 / 标签权重 / 评论甜蜜区 / 新鲜度），按分排序

然后**人工逐条复核**（脚本不替代，以下为补充语义判断）：

- 评论中无人声称 I'll take this / I'm working on this（脚本输出中附认领短语清单供对照）
- 描述清晰，有明确的期望行为或可复现步骤
- 所需改动范围在 1~3 个文件内，不涉及整体架构重构

**输出格式（表格）：**

| Issue # | 标题 | 类型 | 所需技能 | 预估工作量 | 打分 | 推荐理由 |
|---------|------|------|---------|-----------|------|---------|

## 三、分析维度二：架构层缺陷分析（AI Agent 项目专用 7 维度）

深入阅读源码，逐一检查以下 7 个维度。**每个维度必须定位到具体文件和函数，禁止泛泛而谈。**

### 1. 任务规划（Task Planning）

分析项目当前使用的规划范式（ReAct / Plan-and-Execute / CoT / 无显式规划）。重点检查：
- 任务能否被分解为子任务？有无显式的 Plan 生成步骤？
- 子任务执行失败时，是否有动态重规划机制，还是直接报错退出？
- 规划结果是否可被持久化，以支持断点续跑？
- 若项目完全没有规划层，直接依赖 LLM 单步决策，是否存在引入规划层的空间？

### 2. 多 Agent 协作

分析项目的 Agent 拓扑结构。重点检查：
- 当前是单 Agent 还是多 Agent 架构？
- 若是单 Agent：是否存在天然适合拆分为 Orchestrator + Worker 结构的场景？
- 若已是多 Agent：通信协议是什么？角色职责是否清晰？结果聚合策略是否合理？
- Agent 之间是否存在状态共享机制，还是完全无状态地串行调用？

### 3. 上下文管理策略（Context Management）

分析项目如何处理长对话和 token 限制问题。重点检查：
- 当 context 接近模型 token 上限时，策略是什么（硬截断 / 滚动窗口 / 摘要压缩）？
- 压缩或截断策略是否会丢失关键的工具调用历史或中间结果？
- 跨轮次的对话历史如何存储和读取？是否存在冗余或浪费？
- 是否有针对不同类型信息（系统指令 / 工具结果 / 对话历史）的差异化管理策略？

### 4. Human-in-the-loop 机制

分析 Agent 在执行过程中是否支持人工干预。重点检查：
- 遇到低置信度决策或高风险操作（文件写入、外部 API 调用、消息发送等）时，是否有暂停并等待人工确认的机制？
- 是否有 Checkpoint 机制，支持 Agent 执行中断后从断点恢复？
- 人工介入后，Agent 能否将人的反馈融入后续决策，还是只能重头开始？

### 5. Agent 评估框架（Evaluation）

分析项目是否具备系统评估 Agent 表现的能力。重点检查：
- 是否有 eval 模块或测试集？评估粒度是只看最终结果，还是追踪完整 trajectory？
- 是否集成了外部评估工具（LangSmith / Arize / 自定义 pipeline）？
- 工具调用的选择是否正确、参数是否合理，有没有被量化追踪？
- 若完全没有评估机制，引入最小可用 eval pipeline 的改造成本是多少？

### 6. Tool 检索与路由（Tool Retrieval）

分析项目的工具管理和选择机制。重点检查：
- 当前是全量工具注入（所有 tool schema 塞入 system prompt）还是按需检索？
- 若工具数量超过 20 个，是否有向量化检索机制按任务动态选取相关子集？
- 工具的描述质量如何？是否存在语义相似导致 LLM 选择混乱的问题？
- 是否支持 MCP 协议？若不支持，现有 tool 层是否有接入 MCP 的改造空间？

### 7. Streaming 与中间状态可见性

分析 Agent 执行过程的实时可见性。重点检查：
- 是否支持流式输出（streaming token by token）？
- Agent 的中间状态（当前在执行哪个子任务、调用了什么工具、参数是什么）是否对外暴露？
- 是否有事件/状态订阅接口，供前端实时展示 Agent 执行进度？
- 若缺失，现有架构是否支持以低侵入性方式引入 streaming 和状态广播？

### 每个维度的输出格式

- **现状描述：**（定位到具体文件路径 + 函数名）
- **缺陷 / 缺失：**（当前方案存在什么问题，或完全缺失）
- **影响程度：** high / medium / low
- **改进方向：**（1~3 句话，描述可行的改造方案）
- **改动范围：**（预计涉及文件数和代码行量级）
- **面试叙事角度：**（用一句话说明，这个贡献在面试中能体现什么能力）

## 四、附录：非 Agent 项目的通用分析维度

若目标项目不是 AI Agent 类（如 Web 框架、CLI 工具、库），将 7 维度替换为：

1. **错误处理与边界情况**：是否有未捕获异常、静默失败、缺失的输入校验？
2. **测试覆盖**：哪些核心模块缺少单测/集成测试？有无 CI？
3. **文档与示例**：README 是否过时？缺 quickstart / API 示例 / 类型标注？
4. **性能与资源**：有无明显 N+1、重复计算、未关闭资源？
5. **兼容性与依赖**：依赖版本是否过时？支持的运行时版本是否落后？
6. **开发者体验**：错误信息是否可读？日志是否可观测？配置是否合理？
7. **社区债**：长期 open 的 bug、被反复 +1 的 feature request、停滞的 PR 可否接手复活？

输出格式与六段式相同。

## 五、最终输出：Top 3 贡献建议

综合 Issue 筛选与架构分析两个维度，输出优先级排序的建议：

**第 N 名：{PR 方向名称}**
- 一句话描述：
- 来源维度：Issue #xxx / 代码分析-维度X
- 入口文件：
- 为什么适合我：（结合用户技术栈说明）
- 预计工作量：小 / 中 / 大
- 面试中能讲什么：（具体说明能体现的技术决策和工程能力）
- 风险点：（可能遇到的阻力或依赖）

最后请用户选定一个方向，再决定是否进入 `contribution-workflow.md` 的方案设计阶段。
